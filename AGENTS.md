# AGENTS.md

- Repo: https://github.com/jacobfvanzyl/pgkv
- pgkv is a PostgreSQL Trusted Language Extension (TLE) packaged to follow pg_tle conventions: https://github.com/aws/pg_tle
- Keep versioned install scripts (`pgkv--X.Y.Z.sql`) and upgrade paths (`pgkv--old--new.sql`) in sync with `pgkv.control` `default_version`; `relocatable = false` because SQL hardcodes the `pgkv` schema.
- Before release, verify both direct install and upgrade path:
  - `CREATE EXTENSION pgkv;`
  - `CREATE EXTENSION pgkv VERSION 'old'; ALTER EXTENSION pgkv UPDATE TO 'new';`
- Run `./stress/run-stress.sh` and pgTAP tests before committing. `stress/test_atomicity.py` holds the two-session tests: a function that reads a key and then writes it needs one there.
- From 0.4.0 the versioned scripts are generated: edit the files in `sql/` and run `./build.sh`, which writes `pgkv--<version>.sql` and the upgrade script from the previous version. Never edit the generated files by hand; CI fails if they are out of date. A function whose signature or return type changes must be added to the `DROP FUNCTION` list in `sql/upgrade-*-data.sql`; `tests/14-upgrade-040.sql` fails if an upgraded install differs from a fresh one.
- Redis is the specification. `./conformance/run.sh` replays commands against a real Redis server and against `pgkv.call` and fails on any difference in a reply or in the data left behind. Run it after changing a command; a difference that is kept on purpose goes in `conformance/expected.json` with its reason, and in the README under "Differences from Redis".
- `pgkv.call`, `pgkv.try_call` and `pgkv.pipeline` are the contract the clients in `clients/` are built on (reply encoding, `{"status"}` / `{"error"}` markers, SQLSTATE class `KV`). Changing it means changing both clients and their tests.
- Collections live in side tables keyed by `pgkv.store.id`; the key's row in `pgkv.store` is the lock for the whole collection and carries its element count. Every write to a collection must go through `pgkv._open` (or `pgkv._lock_key`) and finish with `pgkv._save`, and anything that removes or replaces a key must remove its elements (`pgkv._drop_elems`). The conformance harness checks these invariants after every sequence.
- pgkv is closed by default: `sql/99-grants.sql` revokes everything from `PUBLIC`, and roles get access through `pgkv.grant_access` (`sql/95-access.sql`), which grants every function that is not internal (underscore name) and not on its maintenance list. A new owner-only function goes on that list. Extension scripts must never `GRANT` to a user's role: PostgreSQL records privileges set during `CREATE`/`ALTER EXTENSION` in `pg_init_privs` and `pg_dump` then omits them. An upgrade script revokes `PUBLIC` from the functions it adds (they are executable by `PUBLIC` otherwise) and the owner re-runs `grant_access`.
